# How this repository runs OpenWiki

This `openwiki/` tree is generated by [OpenWiki](https://github.com/langchain-ai/openwiki)
against this repository's own source. This page describes the mechanics of *running* OpenWiki
here — not OpenWiki's own internals.

## Local init, then CI update only

The root [`README.md`](/README.md) and [`CLAUDE.md`](/CLAUDE.md) both state the same rule:
**the first `--init` run is local; do not run `--init` in CI.** From the repository root, with
an Anthropic API key in the environment:

```bash
export OPENWIKI_PROVIDER=anthropic
export OPENWIKI_MODEL_ID=claude-sonnet-5
export OPENWIKI_TELEMETRY_DISABLED=1
export DO_NOT_TRACK=1
openwiki code --init --print
```

The generated `openwiki/` pages are then committed to the repository on that branch. Every
later refresh — by a human or by CI — uses `openwiki code --update --print` instead of
`--init`, which diffs against what was last documented rather than starting over.
[`.env.example`](/.env.example) carries the same four environment variables (values only,
no secret) as a copyable template.

## The `OpenWiki Update` GitHub Actions workflow

`.github/workflows/openwiki-update.yml` runs the update on a schedule (`0 8 * * 1` — weekly,
Monday 08:00 UTC) and on manual dispatch. It declares `concurrency: {group: openwiki-update,
cancel-in-progress: true}`, so a manually dispatched run cancels an in-flight scheduled run (or
vice versa) rather than letting two updates race against the same `openwiki/` tree. Its header
comment explains several deliberate departures from OpenWiki's own example workflow, each tied
to this repository's governance:

- **Requires a prior local init.** The job's first real step fails fast if
  `openwiki/.last-update.json` is missing, with the message "Run `openwiki code --init` locally
  and commit `openwiki/` before CI `--update`." — enforcing the local-init-first rule above at
  the CI level, not just in documentation.
- **Requires the `ANTHROPIC_API_KEY` repository secret.** Checked explicitly before anything
  else runs, so a missing secret fails with a clear message instead of a cryptic downstream
  error.
- **Never pushes to `main` directly.** The job opens a **pull request** with its changes,
  consistent with the [GitHub ruleset](../governance/hooks-and-commits.md#the-github-ruleset-on-main)
  that requires a PR for every change to `main` — even an automated one.
- **Restores its own hardened workflow file after every run.** `openwiki --update` is documented
  upstream to rewrite the workflow file that invoked it from its own template
  (`langchain-ai/openwiki#423`); this job explicitly runs `git checkout --
  .github/workflows/openwiki-update.yml` after the update step so the hardened version below
  survives.
- **Only GitHub-owned/verified Actions, SHA-pinned.** Rather than using OpenWiki's example
  third-party `create-pull-request` Action, this workflow uses `gh` (present on the runner) to
  open the PR directly, keeping every Action reference within this repository's
  [SHA-pinning policy](security-automation.md#sha-pinned-actions).
- **Telemetry stays off.** `OPENWIKI_TELEMETRY_DISABLED=1` and `DO_NOT_TRACK=1` are set for the
  run, matching the local-init environment above; the header comment states plainly "this
  public marketplace must not send traces off-box."
- **Scoped to the canonical repository.** The job's `if:` condition checks
  `github.repository == 'cjbischoff/cjbischoff-claude-code-tools'` so a fork cannot
  accidentally arm a weekly Anthropic-billed job using its own secrets.
- **Least-privilege by default.** `permissions: {}` at the workflow level; the job itself
  declares only `contents: write` and `pull-requests: write`, the minimum needed to open the
  update PR (see [security automation](security-automation.md#the-default-read-only-workflow-token)).

## The bounded history digest (`scripts/openwiki-history-digest.sh`)

A `--update` run cannot read git history directly: `.openwikiignore` has active rules, and
OpenWiki restricts shell execution to `pwd`, `git rev-parse HEAD`, and deleting its own plan
file while those rules are active. `scripts/openwiki-history-digest.sh` closes that gap by
running as a separate workflow step, **before** OpenWiki starts, and writing
`.openwiki-history.md` at the repository root for the agent to read with its normal file tools.
It needs `jq` and compares `openwiki/.last-update.json`'s recorded `gitHead` against the current
`HEAD`, then writes:

- one line per non-merge commit in that range, newest first — capped at
  `OPENWIKI_HISTORY_MAX_COMMITS` commits (default 400);
- the net list of changed files across the whole range, excluding `openwiki/` itself (which the
  agent inspects directly) — capped at `OPENWIKI_HISTORY_MAX_FILES` files (default 400).

The digest carries **no patches by design** — it routes the agent's attention to *what* changed
and names the files to re-read in their current form, rather than asserting what the code now
does from a diff alone (a patch can go stale the moment a later commit in the same range touches
the same lines). When either cap truncates the output, the digest says so explicitly, and the
omitted commits/files must be treated as unknown rather than as unchanged — this repository's
own [`openwiki/INSTRUCTIONS.md`](/openwiki/INSTRUCTIONS.md) brief states that rule for exactly
this reason. If `openwiki/.last-update.json` has no prior `gitHead` (a fresh `--init`), or the
digest file is absent entirely (a local run that skipped this step), the brief instructs falling
back to inspecting recent history selectively rather than inventing a change list.

## `openwiki/INSTRUCTIONS.md` and `.openwikiignore`

`openwiki/INSTRUCTIONS.md` is the **user-authored wiki brief** this page's sibling pages were
generated from — OpenWiki reads it on `--init` and `--update` but does not rewrite it during a
normal run. `.openwikiignore` is a **separate read boundary from `.gitignore`**: it tells
OpenWiki which paths to exclude from wiki generation (caches, secrets, the intentionally
vulnerable detector fixtures, local dogfooding/GSD notes, and generated scan artifacts) even
though some of those paths are otherwise tracked in git. Both files are explicitly listed in
the root README's Artifact inventory table and are not generated content — they are inputs to
this process, not outputs of it.
