  <decision>Where the general-defect class and the non-receipt disposition live, given that `models.py` is a frozen byte-mirrored contract</decision>

  <context>
D-11 rates this one-way for the frozen contract: `models.py` and `evidence.py` are
byte-mirrored by the Go port, so anything added there cannot be taken back without breaking
the mirror. `models.Finding` already carries a `cls` field and a `FindingStatus` enum, which
makes reusing them the obvious-looking move and the exact move D-11 forbids. The enum has no
`unconfirmed` member today, and RESEARCH.md names inventing one as Pitfall 5.

Downstream, plan 03-05 attaches the receipt-gate disposition ladder to whatever this
decision produces, and the review ledger's schema follows from it. Picking wrong here means
either a broken Go mirror or a second refactor across two plans.
  </context>

  <options>
    <option id="option-a">
      <name>New `review_findings.py` module with a `ReviewFinding` wrapper (recommended)</name>
      <pros>
        `models.Finding` is untouched and the Go mirror holds. The wrapper carries
        `defect_class`, `disposition`, and `profile` beside the original finding rather than
        inside it. `GENERAL_DEFECT_CLASSES` and `REVIEW_DISPOSITIONS` are module frozensets,
        matching how `evidence.py` already keeps `TIER1_RECEIPTS` and `SHIPPING_STATUSES`.
        Review-mode concepts stay in review-mode code, so the audit path is unaffected.
      </pros>
      <cons>
        One more module and one more indirection when reading a finding's disposition.
        Report and ledger code must unwrap the wrapper.
      </cons>
    </option>
    <option id="option-b">
      <name>Extend `phase_gate.py` with a `ReviewVerdict` dataclass</name>
      <pros>
        No new module; review-mode structures already live there beside
        `review_position_gate` and `DroppedFinding`.
      </pros>
      <cons>
        `phase_gate.py` already owns two distinct jobs — audit phase checks and the review
        position gate — and this would add a third. Growing it further makes the module the
        obvious next thing to split.
      </cons>
    </option>
    <option id="option-c">
      <name>Carry the class only in the review ledger dict, with no typed structure</name>
      <pros>
        Smallest diff. No new dataclass at all.
      </pros>
      <cons>
        The class becomes an untyped string in a dict, so the receipt-gate ladder in plan
        03-05 gets no static checking and `ty` cannot catch a typo in a class name. The
        allowlist bypass would be driven by stringly-typed data at the exact point where a
        wrong value silently widens a security gate.
      </cons>
    </option>
  </options>

  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>

`review_findings.py` defines `GENERAL_DEFECT_CLASSES` as a frozenset of the five rule-doc
classes RULE-05 names, `PROFILES` as a frozenset of `security` and `general`, and
`REVIEW_DISPOSITIONS` as a frozenset holding the review-mode disposition strings. Model the
module on `evidence.py`: frozensets plus small pure predicates, no I/O, no state.

`classify(finding)` maps a finding's rule-doc class onto the allowlist, returning `None`
when it is not a general-defect class. Keep the mapping data-driven so adding a class later
is a one-line edit.

`apply_profile(findings, profile)` raises `ValueError` on an unknown profile — never default
silently, since a typo'd profile that silently ran `general` would widen a security gate.
Under `security` it drops every finding the A-E gates marked, exactly as before this phase.
Under `general` it retains a finding the A or B gate marked only when `classify` returns a
class in the allowlist; every other A/B-marked finding is still dropped, and every C, D, and
E marking drops the finding under both profiles. Return the kept `ReviewFinding` list and a
`DroppedFinding` list matching `phase_gate`'s existing dataclass so the report path needs no
new rendering branch. Sort drops by `(path, line, rule_id)` as `phase_gate` does.

`apply_profile` returns a 2-tuple rather than the `(kept, dropped, declines)` 3-tuple
`review_position_gate` returns, and this divergence from the analog is deliberate: profile
gating is a pure allowlist decision over an already-positioned finding, so it can never
produce a decline. Positioning is the only stage that can be unsure of a location, and it has
already emitted its declines by the time `apply_profile` runs. Returning a third element that
is always empty would invite a caller to believe declines can originate here. State this in
the module docstring so the next reader does not "fix" the shape back to three elements.

Nothing in this module assigns `confirmed`. The mechanical receipt gate in
`findings_gate.py` remains the only place a finding can reach a shipping status; plan 03-05
attaches the disposition ladder for findings without a Tier-1 receipt.

In `references/prompt-constants.md`, add a `GENERAL_PROFILE_EXCLUSION_RULES` block beside
the existing EXCLUSION_RULES block. Leave the existing block byte-for-byte unchanged — the
security profile's no-regression guarantee depends on it. The new block restates gates A
and B qualified by the general-defect allowlist and repeats gates C, D, and E verbatim.
`EXCLUSION_BLOCK_BY_PROFILE` in `review_findings.py` names the two blocks so the skill text
and the code cannot drift apart.

In `SKILL.md`, add the line selecting which block to inject based on the `--profile` value.

In `cli.py`, call `apply_profile` between `review_position_gate` and the report write, and
thread the profile through. In `report.py`, record each surviving record's `profile` and
`defect_class` in the review ledger, as additional keys in the existing dict.
