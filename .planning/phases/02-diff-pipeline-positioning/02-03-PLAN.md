  <behavior>
- A single-hunk diff yields one `Hunk` with the four header numbers parsed.
- A multi-hunk diff yields hunks in file order with independent line numbering.
- A header with an absent old-side count and an absent new-side count treats both as 1.
- A header with a zero new-side count yields no added lines.
- Lines before the first header are ignored, including the `diff --git`, index, and
  `---` / `+++` file-header lines.
- A `+++` file-header line is not counted as an added line, and a `---` file-header line is
  not counted as a deleted line; this is asserted explicitly because both share a prefix with
  real added and deleted lines.
- A leading-plus line becomes an added line whose new-side number advances correctly across
  interleaved context and deleted lines.
- A leading-minus line becomes a deleted line and does not advance the new-side number.
- A context line advances the new-side number and is stored with its leading marker stripped.
- The no-newline-at-end-of-file marker line is skipped and does not become any line kind.
- A diff whose body uses CRLF endings parses with no carriage return surviving into a stored
  line, and no CRLF artifact becomes an added line.
- A diff body with zero headers yields an empty hunk list; `added_line_numbers` on it returns
  an empty set and `line_in_hunk` returns `False` for every line.
- `added_line_numbers` returns exactly the new-side numbers of added lines.
- `line_in_hunk` returns `True` for the first and last new-side line of a hunk's range and
  `False` one line outside either end.
- `hunk_for_line` returns the containing hunk or `None`.
- `parse_hunks` called twice on the same text returns equal results.
  </behavior>
  <action>
Complete `parse_hunks` to the classification rules read from the OCR hunk source. Walk the
body once; ignore every line until the first header matches; on a header, start a new `Hunk`
with the four numbers, defaulting an absent count to 1. Track the new-side line number: a
leading-plus line records an added line at the current number and advances it; a leading-minus
line records a deleted line and does not advance; any other line records a context line with
its first character stripped and advances.

Guard the file-header lines explicitly. `+++` and `---` lines share a prefix with added and
deleted body lines, and the guard is that they can only appear before the first header, which
the ignore-until-first-header rule already covers — assert it rather than assume it, because a
diff body can legally contain a line whose content begins with those characters.

Add `NO_NEWLINE_MARKER` as a module constant for the no-newline sentinel and skip a body line
equal to it without classifying it as any kind.

Normalise line endings before classification so a CRLF diff and an LF diff of the same change
produce identical hunks, and no carriage return survives into a stored line.

Make `Hunk` fully immutable: a frozen dataclass whose `added`, `context`, and `deleted`
collections are tuples, not lists. Immutability is what makes the repeat-call equality
behavior hold and what lets one parsed diff be shared by the positioning and gate stages
without a defensive copy.

Complete `added_line_numbers`, `line_in_hunk`, and `hunk_for_line` against the new-side
numbering, and say so in each docstring — a reader who assumes old-side numbering gets an
off-by-N, and this is the numbering the positioning ladder and the review gate both consume.

Write `tests/test_diffhunks.py` covering every behavior above with inline diff-text fixtures.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Run process -> `artifacts/coverage_manifest.json` | The manifest is the run's persisted coverage claim and a Phase 4 resume input. |
| `git diff` stdout -> `parse_hunks` | Diff text from an arbitrary repository drives which lines are considered reviewable. |
| Manifest file -> external reader | A concurrent or later reader may open the file mid-run. |
