<objective>
Make a resumed review run prove it is the same run before it is allowed to add to
the prior run's coverage, and pin every read to the SHAs that run sealed.

Purpose: without an identity check, resuming under a different model or profile
launders one reviewer's coverage as another's — the manifest would claim complete
coverage that no single configuration ever produced. The check is only worth
anything if a rejection leaves the prior state untouched, which makes ordering,
not comparison, the hard part.
Output: a persisted model and profile identity, a pre-write comparison that
refuses a mismatch, and SHA-pinned reads on resume.
</objective>

  <decision>
    Does the model and profile identity live inside the existing coverage manifest,
    or in a new sibling artifact next to it?
  </decision>
  <context>
    RESEARCH.md flags this as a fork that must not be decided silently, because both
    options are defensible and the choice fixes a consumer-facing artifact shape.
    The coverage manifest is already the run's honesty record and is already embedded
    in `review_comments.json`, so putting identity inside it makes identity travel
    with every consumer for free — at the cost of a manifest schema version bump that
    any existing reader of `coverage_manifest.json` sees. A sibling artifact leaves
    the manifest's shape frozen but adds a second file that can go missing or drift
    out of step with the manifest it describes.

    Prior phases resolved every comparable "we need one more field" question by adding
    a sibling module rather than touching a frozen contract — but that precedent was
    about `models.py`, which is byte-mirrored by a Go port. `coverage_manifest.json`
    carries an explicit `version` key and a `load` classmethod that already reads
    optional fields with `.get` defaults, which is what a schema that expects to
    evolve looks like.
  </context>
  <options>
    <option id="option-a">
      <name>Extend CoverageManifest with model and profile</name>
      <pros>
        One artifact, one write, one atomic replace — identity and coverage can never
        disagree. `load`'s existing `.get` style reads the new fields with a `None`
        default, so an old manifest still loads. Identity reaches every consumer of
        `review_comments.json` with no extra wiring.
      </pros>
      <cons>
        `MANIFEST_VERSION` goes to 2 and `to_dict()` gains two keys, which is a
        visible change to a shipped artifact shape. Any reader asserting the exact
        five-key set breaks.
      </cons>
    </option>
    <option id="option-b">
      <name>New review_identity.json sibling artifact</name>
      <pros>
        `coverage_manifest.json`'s shape and version stay frozen, so no existing
        reader is affected. The identity concern lives in its own small module with
        its own tests.
      </pros>
      <cons>
        Two artifacts that must agree, with no mechanism forcing them to: a manifest
        can outlive its identity file or vice versa. Identity does not reach
        `review_comments.json` without extra wiring. One more file in the sidecar for
        a two-field record.
      </cons>
    </option>
  </options>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| prior on-disk state → resumed run | The persisted identity and SHAs are read back from a file that may have been written by a different configuration, edited by hand, or left by an interrupted run. |
| operator CLI arguments → resumed run | `--profile` and the invoking model are what the identity check compares against; a mismatch is the threat, not an error. |
| resumed run → coverage manifest | Adding to a prior run's coverage under a different configuration is the specific misattribution this requirement closes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-10 | Spoofing | resumed `run_review` | high | mitigate | The persisted model identity and profile are compared field by field before the manifest is constructed; a mismatch exits non-zero naming the differing field, and no override exists (Task 2). |
| T-04-11 | Tampering | prior coverage state | high | mitigate | The comparison strictly precedes every write, so a refused resume leaves the prior artifact byte-identical — asserted by a byte-hash test rather than by inspection (Task 2). |
| T-04-12 | Tampering | persisted SHA reuse | high | mitigate | Each persisted SHA is round-tripped through `resolve_ref_sha`, so a rewritten or collected SHA fails the run instead of reading a different tree as an empty diff (Task 3). |
| T-04-13 | Repudiation | a hand-edited prior artifact | medium | accept | The workspace sidecar is operator-writable by design and the harness cannot sign it; the identity check raises the cost of an accidental mismatch, and a deliberate edit is out of scope at ASVS level 1. |
| T-04-05 | Tampering | `sec_overlay.models`, `sec_overlay.evidence` | high | mitigate | Both stay untouched; identity lives in the coverage artifact or a sibling, never as a new `Finding` field or `FindingStatus` member. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed; `hashlib` and `json` are stdlib and `pyproject.toml` keeps an empty dependency list. |
</threat_model>
