# Phase 04.1: Close gap: DIFF-04 — review sidecar workspace isolation - Research

**Researched:** 2026-08-19
**Domain:** Internal Python CLI wiring fix (sec-overlay plugin, stdlib-only)
**Confidence:** HIGH

## Summary

`run_review` in `plugins/sec-overlay/skills/sec-overlay/helpers/sec_overlay/cli.py` builds its
`Workspace` directly on the caller-supplied repo root (`Workspace(root)`, line 173) instead of
resolving it through `RepoMemory.for_target(...)` the way `scan` and `audit` already do
(cli.py:407-411, 436-440) `[VERIFIED: plugins/sec-overlay/skills/sec-overlay/helpers/sec_overlay/cli.py:172-174]`.
The result: every `review` artifact (coverage manifest, review ledger, review plan, prompt files)
lands inside the reviewed repo's own tracked working tree instead of the git-ignored
`.sec-overlay/<slug>/` sidecar. This is the milestone audit's sole BLOCKER
(`.planning/v5.0-MILESTONE-AUDIT.md` gaps.requirements[DIFF-04], gaps.integration[0]).

This is not an architecture problem. `Workspace` (`workspace.py`) is already sidecar-agnostic —
every property (`kb`, `artifacts`, `runs`, `reports`, `findings_dir`) derives purely from
`self.root`. `RepoMemory.for_target` (`repo_memory.py:116-130`) is already the proven
root-to-sidecar resolver used by two of the three CLI verbs. The fix is to make `run_review`
build `ws` the same way `scan`/`audit` build it — no new module, no new dependency, no new CLI
flag required by the requirement text itself.

The real weight of this phase is not the 3-line production fix; it is the **test-side blast
radius**. Ten call sites across three test files construct `Workspace(root)` or
`Workspace(str(tmp_path))` directly on the bare root and assert paths under it — these tests
currently *encode the bug as correct behavior* and must be rewritten to read through
`RepoMemory.for_target(root, ...).workspace` instead, or they will pass for the wrong reason (or
begin failing) once the fix lands. Two documentation files (`SKILL.md`, `helpers/README.md`)
also state or imply the review verb writes into the target root and need a same-commit update
per this repo's doc-tracks-code governance rule.

**Primary recommendation:** Change only `cli.py`'s `run_review` workspace construction (mirror
the `scan`/`audit` pattern using the already-imported `RepoMemory`), update every test that
constructs `Workspace` directly on a bare root to go through `RepoMemory.for_target` instead, add
one regression test asserting the sidecar convention (mirroring `test_scan_defaults_to_repo_memory`),
and update `SKILL.md` + `helpers/README.md` in the same commit. Do not add a `--workspace` flag to
`review` unless the user/planner explicitly wants CLI parity with `scan`/`audit` — DIFF-04's text
does not require it (see Open Questions).

### Anti-Patterns to Avoid

- **Reimplementing slug/path derivation inside `run_review`:** don't hand-roll a new
  `<root>/.sec-overlay/...` string join in `cli.py` — call `RepoMemory.for_target` /
  `RepoMemory.ensure`, exactly as `scan`/`audit` do. A second implementation of the same
  resolution logic is itself an integration-drift risk (the type of bug DIFF-04 already is).
- **Fixing only `cli.py` and leaving the tests unchanged:** the existing tests construct
  `Workspace(root)`/`Workspace(str(tmp_path))` directly and will keep "passing" against the wrong
  path, or start failing with unhelpful assertion errors, unless they're rewritten to route
  through `RepoMemory.for_target(...).workspace` (see Common Pitfalls).
- **Changing `run_review`'s function signature to accept a `RepoMemory` instead of a root
  string:** unnecessary scope expansion. `run_review` already takes `root`; resolve the sidecar
  `ws` at the call site inside `main()` (matching `scan`/`audit`'s existing structure) and pass the
  resolved `ws` in, or resolve it as the first lines of `run_review` itself — either mirrors the
  existing pattern with a minimal diff.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Deriving a stable per-repo sidecar directory | A new path-join / hashing scheme in `cli.py` | `RepoMemory.for_target(target, runner=...)` (`repo_memory.py:116-130`) | Already proven correct by `scan`/`audit`'s existing tests; a second implementation risks re-introducing exactly this class of drift bug |
| Seeding a self-ignoring `.gitignore` for the sidecar | Writing `.gitignore` content inline in `run_review` | `RepoMemory.ensure(target=...)` (`repo_memory.py:147-177`) | Already idempotent (only writes if absent) and already tested |

**Key insight:** every primitive this fix needs already exists and is already exercised by two of
the three CLI verbs. The task is wiring, not invention — consistent with Ponytail's "already in
this codebase → reuse it" rung.

## Common Pitfalls

### Pitfall 1: Existing tests encode the bug as expected behavior

**What goes wrong:** Ten `run_review(...)` call sites in `test_cli.py` pass `str(tmp_path)`
directly as `root`
`[VERIFIED: plugins/sec-overlay/skills/sec-overlay/helpers/tests/test_cli.py — run_review(...) called with str(tmp_path) at lines 115, 144, 155, 163, 173, 188, 199, 207, 236, 267]`,
and two of those tests then assert against `Workspace(str(tmp_path))` directly, e.g.:

```python
# Source: plugins/sec-overlay/skills/sec-overlay/helpers/tests/test_cli.py:239
ws = Workspace(str(tmp_path))
ledger = json.loads((ws.artifacts / "review_ledger.json").read_text())
```
`[VERIFIED: plugins/sec-overlay/skills/sec-overlay/helpers/tests/test_cli.py:239]`

The `test_review_live.py` helper that seeds a recorded agent return does the same:

```python
# Source: plugins/sec-overlay/skills/sec-overlay/helpers/tests/test_review_live.py:80-85
def _record_return(root, path, *, base=_BASE_SHA, head=_HEAD_SHA, calls):
    ws = Workspace(root)
    ws.ensure()
    envelope = json.dumps({"base": base, "head": head, "response": json.dumps(calls)})
    record_agent_return(ws, agent_label(path), envelope)
```
`[VERIFIED: plugins/sec-overlay/skills/sec-overlay/helpers/tests/test_review_live.py:80-85]`

Once `run_review` reads its recorded return through the sidecar `ws`, this helper writing to the
bare-root `ws` means the recorded return is invisible to `run_review` — tests would start hitting
the `ReviewSourceSkip`/`review_source_skipped` fail-open path (D-15) instead of the expected
finding, likely as a silent behavior change rather than an obvious crash.

**Why it happens:** the bug in production code and the test helpers were both written against
the same (incorrect) assumption — `root` is where artifacts live — so the tests never had a
chance to catch the drift.

**How to avoid:** rewrite every test/helper that builds `Workspace(root)` or
`Workspace(str(tmp_path))` directly to instead resolve via
`RepoMemory.for_target(root, runner=<fake or real>).workspace`, matching the existing template
`test_scan_defaults_to_repo_memory` (`test_cli.py:24-36`), which sets `SEC_OVERLAY_HOME` via
monkeypatch and asserts the slug directory contents rather than a bare-root path.

**Warning signs:** any `grep -n "Workspace(" tests/` hit that is not immediately followed by
`RepoMemory` in the same test — a manual check pass over all matches is required, not just a fix
to `cli.py` alone.

### Pitfall 2: Fake `runner`/`subprocess.run` shapes must tolerate `repo_slug`'s git commands

**What goes wrong:** `repo_slug` issues `["git", "-C", str(target), "remote", "get-url", "origin"]`
and conditionally `["git", "-C", str(target), "rev-parse", "--show-toplevel"]`
`[VERIFIED: plugins/sec-overlay/skills/sec-overlay/helpers/sec_overlay/repo_memory.py:67-107]`.
Any fake runner used in `review` tests that pattern-matches on `cmd[1]` (e.g. checking for
`"--verify"`, `"--name-status"`, `"show"`) must not crash on this new call shape.

**Why it happens:** wiring `RepoMemory.for_target` into `run_review` means every `review` test now
indirectly exercises `repo_slug`'s subprocess calls, which none of them did before.

**How to avoid:** confirmed safe by direct inspection — `_make_review_runner` in `test_cli.py`
(lines 76-89) and the `_fake_run_for` helper in `test_review_live.py` (lines 58-77) both fall
through to a default success/empty-stdout result (`_FakeResult("")`, returncode 0) for any
unmatched command shape, and `repo_slug` only takes its git-remote branch when
`res.returncode == 0 and url` is truthy — empty stdout is falsy, so it safely falls back to the
absolute-path identity. No fake runner needs modification for this reason; this check simply
must be re-confirmed once new/updated tests are written, since a change to fallback behavior in
either helper would silently break this invariant.

**Warning signs:** a new test failure with a `KeyError`/`IndexError` inside `repo_slug` or an
unexpected slug value in an assertion — indicates the fake runner's fallback branch was changed
or the test forgot to inject one at all (falling through to the real `subprocess.run`, which would
pick up the *actual* git remote of this monorepo during test runs — a flaky, environment-
dependent slug).

### Pitfall 3: Consistency of `root` across the three-step `--prepare` → dispatch → consume workflow

**What goes wrong:** `repo_slug` hashes an identity string built from the git remote or, absent
one, `str(Path(target).resolve())`
`[VERIFIED: plugins/sec-overlay/skills/sec-overlay/helpers/sec_overlay/repo_memory.py:67-107]`.
If the three steps of the review workflow (`--prepare`, agent dispatch, final consume run) are
invoked with a differently-spelled or unresolved `--root` (e.g. relative vs. absolute, or a
symlinked path resolved differently across invocations), the resolved sidecar slug could differ
between steps, silently orphaning the prepared plan/prompts from the consuming run.

**Why it happens:** this was not previously an issue because every step wrote into the bare
target root directly — no slug resolution existed to diverge.

**How to avoid:** document in `SKILL.md` that all three review-workflow invocations (`--prepare`,
dispatch, and the final consuming run) must pass the identical `--root` value (same string,
ideally an absolute path) so `RepoMemory.for_target` resolves to the same slug every time. No code
change is required for this — it is a documentation/usage-discipline item since `repo_slug`
already resolves paths to absolute form before hashing, minimizing (but not eliminating) the
divergence risk for genuinely equivalent paths.
